# Yard Web jobs contract

Status: implemented; the contract of the "Web runs every CLI action" effort and the single
reference for its three pieces:

- **T1, host executor**: a new hidden `yard ops-server` subcommand and its systemd unit;
- **T2, Web API**: the job and log endpoints in `web/server/`;
- **T6, UI**: the React client in `web/ui/`.

Where this document and the CLI disagree about the CLI, the CLI wins and this document gets fixed.
[web.md](web.md) describes the architecture, installation and security model.

Auth is unchanged: Caddy Basic Auth in front of Yard Web. Everything below is
private-network, single-tenant, no roles: any authenticated user may run any action.

## Actions

| `action`       | Scope   | Command executed by the host executor (argv, no shell) |
| -------------- | ------- | ------------------------------------------------------ |
| `deploy`       | project | `yard deploy <project>`                                |
| `backup`       | project | `yard backup <project>`                                |
| `restore`      | project | `yard restore <project> <revision> --yes`              |
| `images-prune` | global  | `yard images --prune --yes`                            |
| `host-collect` | global  | `yard host`                                            |

`rollback` is an alias of `restore` in the CLI and is not exposed. The prune
**dry run is a read, not a job**: `GET /api/read?op=images-prune-plan` runs
`yard images --prune` (without `--yes`) through the existing read socket and
returns `{"output": "..."}` like the other reads (T1 adds the op to
`read_server.rs`; T2 adds it to Web's own allowlist). The UI must show it before
offering the real prune.

Argument rules (enforced by Web, then again by the executor):

- `project`: required for project actions, **forbidden** for global actions. It must be
  `[A-Za-z0-9_-]{1,64}`, a configured project, with a full manifest (not a URL-only monitor), and
  not the reserved name `host`.
- `revision`: required for `restore` (must be one of the project's restore points), forbidden otherwise.
- `confirm`: must be exactly `true` for `restore` and `images-prune` (these map to the
  CLI's `--yes`); ignored for the others. `deploy` and `backup` are not confirmed by the API
  (the UI may still ask).

## Job model

States: `queued` -> `running` -> `succeeded` | `failed`. In v1 the executor does not keep a
queue: a job is accepted only if its lock is free, so `queued` is the very short window
between acceptance and the process being spawned. Clients must still handle it.
`failed` covers non-zero exit, spawn failure, timeout and "executor restarted while running".
There is no cancellation in v1.

The wire shape is the `Job` type (`web/ui/src/api/types/Job.ts`): `id`, `action`, `project`,
`revision`, `state`, `actor`, `created_at_unix`, `started_at_unix`, `finished_at_unix`,
`exit_code`, `output_bytes`, `error`. Ids are generated by the executor, sortable and
URL-safe: `YYYYMMDDTHHMMSSZ-<8 lowercase hex>` (for example `20261019T142501Z-3fa9c01b`).
Sorting ids descending is "newest first".

Locking (executor-side, authoritative):

- one running job per project (`deploy`, `backup`, `restore` of the same project are mutually exclusive);
- `images-prune` and `host-collect` take the **global** lock: they exclude every other job, and
  every job excludes them;
- different projects run concurrently.

A refused lock is `409` with the id of the job holding it.

## Browser <-> Web HTTP API

All bodies are JSON (`application/json; charset=utf-8`), `Cache-Control: no-store`, same
security headers as the existing endpoints. Types come from `web/ui/src/api/types/`.

| Method and path | Purpose | Success |
| --- | --- | --- |
| `POST /api/jobs` | Start a job. Body `CreateJobRequest`: `{action, project?, revision?, confirm?}`, unknown fields rejected. | `202` + `Job` + `Location: /api/jobs/{id}` |
| `GET /api/jobs` | List jobs, newest first. Query `ListJobsQuery`: `project`, `action`, `state`, `limit` (1-200, default 50), `cursor`. | `200` + `JobList {jobs, next_cursor}` |
| `GET /api/jobs/{id}` | One job. | `200` + `Job` |
| `GET /api/jobs/{id}/output` | Job output as SSE (below). | `200 text/event-stream` |
| `GET /api/logs/stream` | Live container logs as SSE (below). Query `project` (required), `service`, `since`, `tail`. | `200 text/event-stream` |
| `GET /api/read?op=images-prune-plan` | Prune dry run (a read). | `200` `{output}` |

`GET /api/jobs` and `GET /api/jobs/{id}` are served from the jobs directory (see "How Web
reads jobs"), so they keep working when the executor is down. `POST` and the log stream need the executor.

### Errors

Every non-2xx response of the endpoints above is an `ApiError`:
`{"error": "<generic message>", "code": "<code>", "running_job_id"?: "<id>"}`. As with the existing
read API, the UI shows only these generic messages, never raw backend text.

| Status | `code` | When |
| --- | --- | --- |
| `400` | `refused` | invalid body/query, unknown field, unknown project, URL-only monitor, missing `revision`/`confirm`, revision not a restore point, bad `since`/`tail` |
| `403` | `forbidden` | CSRF check failed, or the request does not come through the trusted proxy (below) |
| `404` | `not_found` | unknown job id |
| `409` | `conflict` | a job already holds the project or global lock; `running_job_id` is set |
| `503` | `executor_unavailable` | ops (or read, for log streams) socket missing, refused or timed out |
| `429` | `refused` | too many concurrent SSE streams (4 log streams, 32 job output streams per Web instance); retry later |
| `500` | `failed` | unexpected Web error, or an executor `internal` error |

### CSRF and identity

Mutating means any method other than `GET`/`HEAD`. Web has no CORS headers, so cross-origin
scripts cannot read responses or send the custom header. A mutating request is accepted only if:

1. it carries `X-Yard-Request: 1`;
2. if `Sec-Fetch-Site` is present, it is `same-origin`;
3. if `Origin` is present, its host:port equals the request's `Host` (or `X-Forwarded-Host`
   when set by the proxy). A request with neither `Origin` nor `Sec-Fetch-Site` (curl, scripts)
   passes on the custom header alone: those clients are not CSRF vectors.

Otherwise `403 forbidden`. `GET` endpoints, including the SSE ones, never mutate and need no header.

**Actor.** The audit name of a job is the Basic Auth user. Caddy sets two headers on the proxied
request, overwriting anything the client sent (`header_up` replaces, it does not append):

```caddyfile
reverse_proxy yard-web:8088 {
    header_up X-Yard-User {http.auth.user.id}
    header_up X-Yard-Proxy-Token <random secret generated by install-web.sh>
}
```

Yard Web trusts `X-Yard-User` **only** if `X-Yard-Proxy-Token` equals its `YARD_WEB_PROXY_TOKEN`
(compared in constant time). The token stops any other container on the shared Docker network
from forging an identity or reading anything by talking to Web directly: when `YARD_WEB_PROXY_TOKEN` is set, a
missing or wrong token makes every `/api/*` request (GET and SSE included) `403 forbidden`; `/healthz` and
static files stay open. If `YARD_WEB_PROXY_TOKEN` is unset, reads keep working (a plain `docker run` of Web
is a read-only dashboard) and every mutating request is `403 forbidden`. The user name is also validated as `[A-Za-z0-9._@-]{1,64}`.
The header and token are never echoed to the browser and never logged. `Job.actor` is the
validated user name.

### Output stream (SSE)

`GET /api/jobs/{id}/output` responds `text/event-stream` (`Cache-Control: no-store`, `X-Accel-Buffering: no`).
Unknown id is a normal `404` JSON error, before any stream starts.

- `event: state`, `data: <Job JSON>`: sent first, and again whenever state or `output_bytes` changes.
- `event: output`, `id: <next_offset>`, `data: <OutputChunk JSON>` where
  `{offset, next_offset, text}`. Offsets are **byte offsets in the job's log file**. A chunk always
  ends on a line boundary (the final chunk of a finished job may not) and is valid UTF-8 (invalid
  bytes are replaced). The SSE `id` is `next_offset`.
- `event: end`, `data: <Job JSON>`: sent once the job is terminal and the log has been fully
  delivered; the server then closes. The client must not reconnect after `end`.
- `: keepalive` comment every 15 s.

**Resume.** `EventSource` reconnects automatically with `Last-Event-ID: <next_offset>`. A client
may also pass `?offset=<bytes>`; `Last-Event-ID` wins when both are present. Offset 0 or omitted
replays the whole output; an offset beyond the file size starts at the end. Output of finished jobs
can be replayed the same way for as long as the job is retained.

`GET /api/logs/stream` (live `docker compose logs --follow`, via the executor, below):

- `event: line`, `data: {"text": "..."}` (`LogLine`), no `id`: logs are not resumable; a
  reconnecting client sends `since=` itself, or accepts a fresh `tail`.
- `event: end`, `data: {"reason": "closed"|"error"}` (`LogEnd`): the stream is over. `closed`
  means the server time limit was reached; clients may reconnect with `since`.
- `project` required; `service` must be a configured service; `tail` 1-1000 (default 200);
  `since` has the same character restrictions as `/api/read?op=logs`. Violations are `400`
  before the stream starts. Web also reads the executor's first frame (up to 1.5 s) before
  answering `200`: an initial `{"error":...}` line becomes `400` (refused), `429` (executor
  over its 4-stream limit) or `503` (anything else, or the executor closing without a frame) with
  the usual `ApiError` JSON. A first frame that is slow to arrive does not delay the stream: the
  SSE starts anyway.
- Limits: at most 4 concurrent streams per Web instance, 1 hour per stream.

## Web <-> host executor

### Sockets

| Socket | Service | Purpose | Web mount |
| --- | --- | --- | --- |
| `/run/yard-web-read/read.sock` | `yard read-server` (existing) | bounded one-shot reads, plus the new `logs-follow` stream | existing |
| `/run/yard-web-ops/ops.sock` | `yard ops-server` (new, T1) | start jobs | new, directory mount |

The ops socket is **separate** from the read socket so that the read service can keep its
strict profile (`PrivateNetwork`, no job state writes) and so that mutation rights are granted
by an explicit, auditable mount. Same conventions as the read service: a systemd unit
`yard-web-ops.service`, `RuntimeDirectory=yard-web-ops` (mode 0750), dedicated group `yard-web-ops`
that the Web container user joins, `UMask=0007`, `NoNewPrivileges`, and the hardening of `yard-web-read.service` **except** what a
deploy cannot work without. Unlike the reader, the executor runs Docker, Git and project backup commands
and writes `/var/lib/yard`, so it runs as root and relaxes: no `PrivateNetwork` (git, builds, backups
use the network); `ProtectSystem=full` instead of `strict` and no `ProtectHome` (repositories, Compose
directories, backup targets and root's git/docker credentials are chosen by project manifests and
live anywhere; `/usr`, `/boot` and `/etc` stay read-only), so there is no `ReadWritePaths` list;
the capability bounding set is `CAP_DAC_OVERRIDE CAP_DAC_READ_SEARCH CAP_FOWNER CAP_CHOWN` instead of empty
(a root without them cannot work in directories owned by the deploy user); `RestrictAddressFamilies`
adds `AF_INET AF_INET6`. `NoNewPrivileges` stays, so `sudo` inside a backup command does not work.
The unit and installer helpers live in `ops/` (not `web/`). Env: `YARD_WEB_OPS_SOCKET` in Web.

### Wire protocol

One request per connection: a single JSON object on one line (max 4 KiB, `\n`-terminated), one
JSON reply line, then close. Every request struct uses `#[serde(deny_unknown_fields)]`. Read timeout
2 s on the executor; Web uses a 5 s timeout end to end.

```json
{"v":1,"op":"start","action":"restore","project":"hello-api","revision":"abc123","confirm":true,"actor":"corentin"}
{"v":1,"op":"ping"}
```

Replies:

```json
{"ok":true,"job":{ ...Job... }}
{"ok":false,"error":"refused","message":"Unknown project"}
{"ok":false,"error":"conflict","message":"A job is already running","running_job_id":"20261019T142501Z-3fa9c01b"}
{"ok":false,"error":"internal","message":"..."}
```

`start` returns as soon as the job is accepted and persisted as `queued`/`running`; it never waits
for completion. Web maps `refused` -> 400, `conflict` -> 409 (copying `running_job_id`), `internal` -> 500; a connection failure, timeout or malformed reply -> 503. `message` is for logs, never shown to browsers.

The executor trusts nothing from the request beyond what the allowlist accepts:

- `action` is a closed enum (table above); the argv is built from fixed templates, with `project`
  validated like Web does **and** checked against `/etc/yard/projects` (full manifest, not a monitor;
  `backup` also needs a configured backup command), `revision` checked against the project's recorded
  restore points: the `current`, `previous` or `pending` release of its state file, by revision or as
  `release:<tag>`. No shell, no env passthrough: `env_clear`, then `PATH` and `HOME` (inherited from the
  executor, defaults `/usr/local/sbin:...:/bin` and `/root`), the `YARD_*` variables set on the executor unit
  (thresholds) and `YARD_PROJECTS_DIR`/`YARD_STATE_DIR`; stdin `/dev/null`, working directory `/`, umask
  `022` (the unit's `UMask=0007` only protects the socket).
  The binary is the executor's own (`/proc/self/exe`, as in the read executor), not taken from the request:
  jobs always run the same version as the executor, and `update.sh` restarts the unit.
- `actor` is only an audit label supplied by the already-authenticated Web; it is re-validated
  (`[A-Za-z0-9._@-]{1,64}`) and recorded. The socket's file permissions are the real authorization.
- Each job runs in its own process group with a wall-clock timeout (deploy 30 min, restore 30 min,
  backup 60 min, images-prune 10 min, host-collect 2 min); on timeout the group gets `SIGTERM`, then `SIGKILL` after 10 s, and the job is `failed`.
- The output is capped at 16 MiB. After that the executor appends `[output truncated]` once and
  discards the rest (the job keeps running). Stdout and stderr are interleaved into one stream.

### Job storage

Under `/var/lib/yard/jobs/` (created `0755`, files `0644` so the existing read-only state mount works):

- `<id>.json`: the `Job` object plus `"v": 1`. Written **atomically** (temp file in the same directory, `fsync`, `rename`),
  at acceptance, at spawn, and at completion. `output_bytes` is refreshed with the same atomic write (at most
  every second while running, and at the end). Readers never see a torn file.
- `<id>.log`: append-only raw output, created before the process is spawned. Never rewritten or truncated.
  Its size is the source of truth for offsets; `output_bytes` in the JSON may lag while running.

Crash safety: the executor writes the process group of a live job to `<id>.pid` (removed at completion).
When `ops-server` starts, every job still `running`/`queued` whose process group is gone is
marked `failed` (`error: "Executor restarted"`), with `finished_at_unix` set. A group that is somehow still alive
is adopted: it keeps its lock and the job is failed once the group disappears. Locks are in-memory only, derived
from the live set after that sweep. Ids are never reused; `<id>.pid` is not meant to be read by Web.

Retention: terminal jobs older than 90 days (by `finished_at_unix`) are deleted (`.json` and `.log`) at
executor start and daily. Running jobs are never deleted.

### How Web reads jobs and output

**Decision: Web reads `${YARD_STATE_DIR}/jobs/` directly through the read-only mount it already has.**
`/var/lib/yard` is already mounted read-only into Web (`YARD_STATE_DIR`), so no new mount and no new
socket operation is needed, Web's filesystem permissions stay read-only, and the executor stays
small (it only writes files and never streams output). The alternative, streaming the output through the
socket, would need a second long-lived connection protocol, reconnection logic in two processes and would keep
history unreadable while the executor is down. Consequences:

- `GET /api/jobs` lists `jobs/*.json` (ids sort lexicographically, so newest-first is a reverse
  sort of file names; `cursor` is "return ids strictly before this id"), filters in memory, and ignores
  unparsable files. Only `.json` files matching the id pattern are read; the id in the URL is validated against the
  id pattern before it touches the filesystem (no path traversal).
- The output SSE tails `<id>.log` by byte offset (poll about every 250 ms, or inotify if wanted), sends only up to the last `\n`
  while the job is `running`, then flushes the remainder once the metadata is terminal and the file is stable.
- Web never writes in `jobs/`. Only `POST` goes through the socket.
- Job output is whatever the Yard CLI prints (the same data class as `yard logs`); it is shown
  to every authenticated user. The executor must not add secrets to it.

### `logs-follow` on the read socket

Live logs are a read, so they extend the **read** protocol (T1): `{"op":"logs-follow","project":...,"service":...,"since":...,"tail":...}`
validated exactly like `logs`. The reply is a stream of JSON lines `{"line":"..."}` (each line truncated at 16 KiB),
terminated by `{"end":"closed"|"error"}`. The executor spawns `yard logs <project> --follow ...`, and kills its whole process group when the peer
closes the connection or after 1 hour (`{"end":"closed"}`; the command ending by itself is `{"end":"error"}`). At most 4
concurrent follow streams on the reader; a request over the limit, like any refused request, gets a single
`{"error":"..."}` line instead of frames (Web reads it before starting its SSE: refused -> 400, over the limit -> 429, otherwise 503). Web converts frames 1:1
into SSE events.

## Regenerating the TypeScript types

The Rust structs in `web/server/api_types.rs` (jobs) and `web/server/main.rs` (`/api/status`)
derive `ts_rs::TS`. `cargo test` writes `web/ui/src/api/types/*.ts`:

```bash
cargo test --manifest-path web/Cargo.toml     # regenerates the files
git diff --exit-code -- web/ui/src/api/types  # what CI checks
```

Commit the regenerated files with any change to those structs. Never edit them by hand.
Integer fields that fit a JS number are annotated `#[ts(type = "number")]` (ts-rs would emit `bigint`).

## Out of scope for v1

Cancelling a job, a job queue, per-user permissions, multi-host executors, and streaming job
output through the socket.
